1. Overview

MT Alchemy is a People Development Consultancy specialising in Emotional Intelligence, Leadership Development, Team Engagement and Workplace Well-being. Its tagline is "We don't just run activities. We shift mindsets, behaviours, and team culture." The platform turns visitors into enquiries, learners and corporate clients.

Four modules in one application

Corporate website

A single landing page whose menu glides to About, Services, Upskilling, Store, Insights and Contact. It adds founders, impact stories, an EQ self-assessment, a "For organisations" enquiry and a cartoon virtual tour reached by QR code.

Learning management system

A course catalogue filtered by each learner's pathway (career stage and interests), purchase and enrolment, a modular player (video, PDF, reading, quiz), progress tracking, and certificates with a public verification link.

E-commerce store

Digital products download after payment; physical products ship with a tracked Processing, Shipped, Delivered timeline. One checkout handles products, courses and employer seats. Payments run in test mode.

Role-based portals

Five roles (Guest, Individual, Employer, Trainer, Super Admin), each with its own navigation, notifications and permissions enforced by database security rules.

2. Information architecture

The site has one public area and four signed-in portals. The menu (About, Services, Upskilling, Store, Insights, Contact) is available everywhere; on the home page, each item glides to its section of the landing page, and from any other page it opens the full page.

3. System architecture

The application is a single Flutter codebase that talks directly to Firebase. There is no custom server: business rules run in the client stores, and Firestore security rules decide who may read or write each document. Everything is delivered as a static web app (GitHub Pages) that connects to Firebase over HTTPS.

How data flows

  1. Sign-in. AuthStore listens to Firebase Auth. When a user signs in it streams users/{uid} (role, organisation, pathway) and their organisation document.
  2. Fan-out. The other stores listen to AuthStore. When the uid changes they cancel old listeners and subscribe to that user's data, for example enrolments where userId == uid.
  3. Rendering. Screens watch stores and rebuild automatically. CatalogStore starts with the bundled catalogue so pages paint instantly and work offline; Firestore then replaces it live.
  4. Writes. Checkout, assignment and enrolment use batched writes or transactions (stock decrement). Lesson progress updates optimistically, so the interface responds before the server confirms.
  5. Errors. Every action returns a friendly message (for example "That email and password do not match an account.") instead of throwing.

Routing and role guards

Public pages share AppShell: one Scaffold with a glass AppBar and an end drawer below 1024 px. Signed-in pages share PortalShell: a second Scaffold with its own AppBar, a side rail (drawer on small screens), the notification bell, a theme toggle and one scroll area with a visible scrollbar. All portal pages are flat sibling routes, because nested child routes would stack a page underneath that Flutter never lays out.

RoleHome after sign-inGuard
Guestpublic sitePortal paths and /learn redirect to /login?from=…, and return afterwards.
Individual/portal/meMay open only /portal/me/*.
Employer/portal/employerMay open only /portal/employer/*.
Trainer/portal/adminMay open only /portal/admin/*.
Super admin/portal/superMay open /portal/super/* and the trainer's course editor and students pages.

The router waits for Firebase to restore the session before deciding, so a signed-in user is never bounced to the login screen on refresh.

Theme switching

Colour tokens are static getters on the active palette. When the brightness changes, every element is marked for rebuild so each widget re-reads the tokens, without recreating the tree; the current page, scroll position and widget state survive. The toggle reads the live brightness at press time, so it always flips.

5. The five user journeys

A · Individual learning

  1. Register: choose a career stage and interest areas (/register).
  2. The course catalogue shows only courses that match both (/portal/me/courses).
  3. Buy the course, then pay at checkout (test card 4242 4242 4242 4242).
  4. An enrolment is created from the paid order; the dashboard shows progress.
  5. Open the course: watch the video, read the PDF, Mark complete, Next.
  6. Pass the quiz (70% or more) to complete the course and receive a certificate with a public verification link.

B · Digital product

  1. Store, then the EI Self-Coaching Toolkit.
  2. Add to cart, then checkout (no delivery address, no shipping).
  3. A payment record is created in test mode.
  4. My digital products, then Download. The count is tracked.

C · Physical product

  1. Store, then Cart (delivery is free from £50 of shipped goods).
  2. Enter a delivery address at checkout and pay.
  3. Stock is reduced in a transaction; a shipment is created as Processing.
  4. The super admin marks it Shipped (with a tracking number), then Delivered; the buyer is notified each time.

D · Employer

  1. Register an organisation (/register?type=organisation).
  2. Add employees; they join automatically when they register with that email.
  3. Buy courses: choose the number of seats and pay.
  4. Assign courses to people; each assignment uses a seat.
  5. Watch the progress report and the analytics charts update live.

E · Corporate enquiry

  1. Open "For organisations" from the landing page or footer.
  2. Submit the enquiry (saved to Firestore).
  3. The super admin inbox tracks it: New, In discussion, Proposal sent, Programme agreed, Closed.
  4. The admin writes the customised programme proposal.

Staff: free access

  1. A trainer or admin opens any course free (admin preview, nothing is saved).
  2. Courses, then Students shows enrolled, paid, employer seats and free access.
  3. Search a learner and give free access, or remove someone. A removed payer is not refunded automatically.

Key guarantees, each proven by the live verification script: users cannot change their own role; self-registration can only create individual or employer accounts; an enrolment needs a paid order or an assignment; a certificate can be created only when the enrolment is complete; employers cannot touch another organisation's data; draft courses are hidden from everyone except staff; buyers cannot mark their own parcel delivered.

Business rules

RuleBehaviour
Learning pathwayA course is open to a learner only if its level suits their career stage and its practice area is one of their interests. Student: Foundation. Professional: Foundation and Practitioner. Manager: Practitioner and Leader. Senior leader: Leader. Other courses stay visible but locked, with the reason. Employer assignments and staff are not restricted.
Pricing and shippingPrices in GBP. Delivery is £4.95, free from £50 of shipped goods. Digital products and courses never ship.
SeatsAn employer buys seats per course (stored on the organisation). Assigning a course uses one seat per person; the assignment is refused when seats run out.
Progress and certificatesProgress is lessons completed divided by lessons. Quizzes pass at 70% and complete their lesson. Completing every lesson creates the certificate, whose code is built from the first three letters of the course id and the start of the learner id.
PaymentsSimulated gateway in test mode. A card number starting 4000 0000 0000 0002 is declined; any other valid test number is approved. Only the last four digits are stored.
Free accessStaff can create an enrolment with source "granted"; it needs no order and no seat.
Offline fallbackIf Firestore is unreachable the bundled catalogue keeps pages working.

7. Design system, imagery and motion

Colour

Pure white (#FFFFFF), a neutral zinc "ash" scale (#F4F4F5 to #18181B) and Crimson Red #C8102E as the single accent for calls to action, active states, progress and focus. Grey-to-red gradients appear only at moments of change: a passed quiz, a completed order, a finished course. There is no grain texture and no grey haze. A full dark palette mirrors the light one.

Glassmorphism

A shared GlassPanel (backdrop blur, translucent fill, hairline border) is used on the navigation, hero copy, summaries and forms. Few panels per screen, never nested, with a solid fallback for high contrast.

Typography

Fraunces (serif) for headings and Manrope for body text, with a fluid scale (display, h1 to h4, lead, body, small, label).

Imagery

Thirty free-licence photographs (Unsplash, converted to WebP) appear on every course, product, service and article card. Courses and products store an imageUrl that admins can change; the seeded red ink artwork is the fallback. Founder portraits are uploaded from the site.

Motion

  • Landing film with a floating glass crystal and parallax particles
  • Staggered reveals on scroll
  • Every card: hover lift, soft red shadow, photo zoom, press feedback
  • 3D tilt on service cards
  • Fade-and-lift page transitions
  • Smooth glide from menu to landing section
  • Animated EQ result bars, rotating impact stories
  • All of it respects the reduced-motion setting

Accessibility

Semantic labels on icon buttons, live regions on form errors, visible focus, contrast-checked tokens, captions on the tour film, and an explicit table of text in every chart legend.

The QR code

The last section of the landing page shows a QR code that opens the tour. It encodes the site's own address, taken from the browser plus the build's base path, so it is correct on whatever host the site is published to. On a computer's localhost the page warns that the code only opens locally; on the live site it scans from any phone. The same section has an "Open the tour" button and a "Copy link" button.

Troubleshooting

SymptomLikely cause and fix
"You do not have permission to do that."A security rule refused the write. Check the role in users/{uid} and reproduce it in verify.mjs.
Catalogue shows but never updatesFirestore unreachable; the app falls back to the bundled catalogue. Look for "Could not reach Cloud Firestore" in the console.
"requires an index"A new compound query. Follow the link in the error or add it to firestore.indexes.json.
Portal is empty after loginThe profile document is missing. Re-run the seed or create users/{uid} with a role.
QR code opens a blank or wrong addressThe build was made without SITE_BASE; rebuild with deploy_pages.sh.

11. Limitations and future work

AreaCurrent state and the next step
PaymentsSimulated in test mode, with no real charge. Next: a payment provider (Stripe or similar) with a server-side webhook, which needs Cloud Functions.
File storageFirebase Storage needs the paid plan, so PDFs and downloads are served from the site's own /downloads folder, and founder photos are stored in Firestore as small JPEGs. Next: Storage for lesson videos, PDFs and photos.
EmailPassword-reset email is sent by Firebase. Order receipts, employee invitations and enquiry replies are not emailed; people see them in the app (notification bell). Next: transactional email.
CertificatesViewable and verifiable by link; no PDF download button yet.
RefundsRemoving a paying student does not refund them; an admin must handle that with the payment provider.
DevicesVerified in desktop and phone-sized browsers. Native Android and iOS builds use the same code but were not tested on devices.
Browser window fitOne report of the page not filling the window edge to edge on a particular display was not reproduced and remains open.
Hosting deep linksGitHub Pages returns HTTP 404 for deep links before the app loads (the app then renders normally). Firebase Hosting would return 200.
EQ self-assessmentAn engagement tool with ten statements across five areas, not a validated psychometric instrument.
Hero videoAn AI-generated landing clip was deferred; the Remotion films are used instead.
